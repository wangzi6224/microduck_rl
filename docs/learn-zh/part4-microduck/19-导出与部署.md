## 19.1 两个文件

训练每 250 次迭代（和结束时）存两样东西：

| 文件 | 里面有什么 | 给谁用 |
|---|---|---|
| `model_N.pt` | **检查点**（checkpoint）：actor 和 critic 的全部旋钮、两个归一化器的 μ/σ、14 个动作 σ、Adam 的两本账、迭代数 | 继续训练、回放、导出 |
| `xxx.onnx` | 只有 actor：归一化 + 四层 MLP，**输出均值** | 真机 |

实验 `ch19_onnx_vs_torch.py` 打开第 14 章冒烟训练的产物。检查点里 actor 的键：

```
actor_state_dict 里的键        形状
-----------------------  ----------
   obs_normalizer._mean     (1, 61)     ← 第 8 章：61 个 μ
    obs_normalizer._std     (1, 61)     ← 61 个 σ
 distribution.std_param       (14,)     ← 第 4 章：14 个动作噪声 σ
           mlp.0.weight   (512, 61)     ← 第 6 章：四张价格表
           mlp.2.weight  (256, 512)
           mlp.4.weight  (128, 256)
           mlp.6.weight   (14, 128)
```

前 14 章讲的每一个东西都在这张表里。

## 19.2 打开 ONNX：里面就是你学过的九步

**ONNX**（Open Neural Network Exchange）是一个跨框架的模型文件格式：把网络存成"一串算子 + 常数"，支持相应算子和版本的推理运行时可以执行；ONNX Runtime 有多种语言接口，不需要 torch。

实验第 2 节读出的结构：

```
输入 : obs [1, 61]
输出 : actions [1, 14]
算子 : Sub → Div → Gemm → Elu → Gemm → Elu → Gemm → Elu → Gemm
```

| 算子 | 是什么 | 对应章节 |
|---|---|---|
| Sub | $x - \mu$ | 第 8 章归一化 |
| Div | $\div(\sigma + 0.01)$ | 第 8 章 |
| Gemm | 矩阵乘 + 偏置 $W\mathbf{x} + \mathbf{b}$ | 第 2 章、第 6 章 |
| Elu | 门 | 第 6 章 |

9 个算子，2 个归一化 + 4 层 Linear + 3 个 ELU。这是本章示例导出图的结构；不同导出器可能融合或改写等价算子，不能只按算子数量判断正确性。输入名叫 `obs`、输出名叫 `actions`，批大小固定为 1（真机一次只算一帧）。

文件里还带了一份 metadata：`observation_names`（8 块的顺序，第 15 章）、`joint_names`（14 个关节的顺序）、`default_joint_pos`（HOME）、`action_scale`——真机读它们来核对输入输出的约定。

## 19.3 手写 = ONNX，逐位

实验第 4 节从检查点取出 μ、σ、四张 W 和 b，用 numpy 写第 8 + 第 6 章的九步：

```python
x = (obs - mean) / (std + 0.01)
h = elu(W[0] @ x + b[0]); h = elu(W[1] @ h + b[1]); h = elu(W[2] @ h + b[2])
return W[3] @ h + b[3]
```

和 onnxruntime 喂同样的 5 帧随机观测：

```
                                           前 5 个动作
-----------  -----------------------------------------
 numpy 手写  [ 0.0427  0.8462  0.0912 -0.2851  0.726 ]
onnxruntime  [ 0.0427  0.8462  0.0912 -0.2851  0.726 ]
5 帧随机观测的最大差异 = 9.54e-07
```

差异在浮点误差量级。**你现在可以不用任何框架、从零把这个策略写出来。**

## 19.4 部署不采样

第 4 章：训练时动作 = μ + σε。部署时**只用 μ**——实验第 5 节喂同一帧两次，输出完全相同；ONNX 的常数表里也没有 `std_param`。
探索是训练的事，真机上要的是确定、可重复的行为。

## 19.5 忘了烘焙会怎样

第 8 章说这是仓库的不变量。实验第 6 节做了对照：同一帧观测，一个走完整的九步，一个跳过 Sub/Div 直接喂网络：

```
                                            前 5 个动作
------------  -----------------------------------------
烘焙了归一化  [ 0.0757  2.0108  1.248  -1.2672  0.8183]
      没烘焙  [ 0.2018  0.0491 -0.2784 -0.1474  0.0649]
差异 = 1.962 rad ≈ 112°
```

同一帧观测，动作差 112°。而且**在仿真里回放看不出来**（回放脚本自动套归一化器）。这就是为什么必须走 `scripts/export.py`，永远不要手工转检查点。

## 19.6 真机每 0.02 秒的循环

`scripts/infer_policy.py` 是真机运行时的"排练版"：CPU MuJoCo + BAM，不用 GPU，和真机代码一样的观测拼装和动作换算。它的主循环：

```
每 0.02 s：
  ① 读传感器 → 拼 61 维（第 15 章顺序：陀螺仪、重力、关节角−HOME、关节速度、上一步动作、命令）
  ② obs → onnxruntime → 14 个 μ
  ③ 目标角 = HOME + μ × 1.0（第 17 章），送进延迟缓冲
  ④ 物理走 4 小步（每步 BAM 算电压和力矩，第 17 章）
  ⑤ 把 μ 存成"上一步动作"，回到 ①
```

命令块由人来填：走路时 `command[0:3]` 是遥控器的速度指令；`head_command` 是头部目标；`body_command` 保持 0。
**热切换**：走路、站立、起身是不同的 ONNX，共用 61 维输入格式（第 15 章的零填充就是为了这个），运行时按按钮换文件。
有一个经典误会：站立策略把"姿态标志"放在 `command[0]`，全零 = "站着"——所以"按了按钮没反应"往往是命令槽没填对。

## 19.7 再往后：发布到 Hub

## 19.8 导出保存的是“怎样计算”，不是一段录好的动作

检查点里保存参数和训练状态，像一份可继续编辑的工程。
ONNX 保存部署所需的计算与常数，像把运行部分打包成一个可执行函数。
但这个函数仍会每次根据当前观测计算新动作，不是把训练时录下的 14 个角度依次播放。

例如同一个 ONNX，输入“正在前倾”和“正在后倾”两帧，动作通常不同；
同一帧连续输入两次，在确定性执行条件下则相同，因为部署路径取均值，不重新抽探索噪声。
这与“机器人以后每次都走同一条轨迹”不同：真实传感器和物理状态每次都可能不同。

### 模型的边界在哪里

导出的策略内部主要是归一化器与动作均值网络。
它通常不包含整个仿真、奖励、GAE、critic、Adam，也不把 HOME 换算、通信和完整运行时逻辑全部搬进网络。
metadata 中记录 HOME 或 action_scale，不等于 ONNX 的输出已经自动变成绝对角度。
要看输出契约以及运行时在哪里使用这些字段。

所以可以分别检查三个问题：

| 问题 | 检查方法 | 通过后说明什么 |
|---|---|---|
| 算法导出是否一致 | 同一原始观测喂训练侧确定性 actor 与 ONNX，比较逐维输出 | 数值计算路径一致到容差内 |
| 输入输出解释是否一致 | 核对单位、顺序、HOME、命令槽与动作缩放 | 两端使用同一接口含义 |
| 机器人行为是否达到目标 | 实际仿真回放与按场景评估，再按真机流程验证 | 对所测场景的行为证据 |

第一项通过不能替代后两项。随机向量输出一致，也不能证明真实观测都落在训练覆盖范围内。

## 19.9 浮点误差、漏归一化、命令填错，怎样区分

浮点运算精度有限，矩阵累加顺序不同可能让末位出现微小差异。
因此看的是最大绝对误差等数值，并设置适合输出尺度的容差，而不是要求每一位比特完全相同。
一个约 $10^{-6}$ 的差异与漏归一化造成约 1 rad 的差异，量级完全不同。
本章旧示例中的 112° 是那次输入的结果，不是所有漏归一化案例的固定差值。

若数值对比没问题，但按按钮策略像没收到指令，就检查命令进入哪一列。
例如把 posture flag 忘在默认零值，运行时实际仍在要求旧姿态；
这时重新训练网络不一定解决问题，因为网络从未收到“换姿态”的输入。

同样，不同任务都采用 61 维，并不保证它们对 `command[0]` 的解释相同。
维度契约让运行时能够加载模型，任务命令契约才让运行时知道如何驱动它。

## 19.10 从教程实验到部署，应留下哪些可复查的证据

先标明任务 ID、检查点编号与对应 ONNX，避免把早期冒烟模型当成训练完成模型。
导出实验读取的 `.pt` 和 `.onnx` 应来自同一检查点，
不能随意挑“最新两个文件”就认定它们配对；手动多次导出的目录尤其需要核对。

数值等价验证应说明输入、最大误差和容差；接口验证应说明 61/14 维及布局；
行为评估应说明命令、出生姿态、时长和失败现象。
“能跑”“输出一致”“能站 20 秒”“在测试场景能走”是四种不同的证据。

CPU 推理排练是部署路径的检查工具，里面仍有仿真和动作转换，不等于已经在真机上验证。
发布到 Hub 又是文件分发动作，不会自动提高策略质量。
按这种层次记录，你就能定位问题出在训练、转换、运行时解释还是物理迁移。

**自测**：ONNX 输入维数正确、随机输入与 PyTorch 输出一致，能直接说 sim2real 成功吗？

**解释**：不能。它证明了这些输入上的数值转换一致；传感器坐标、命令语义、延迟、执行器和真实行为还需要各自的证据。

## 本章小结

- **检查点** `model_N.pt`：全部旋钮 + 归一化统计 + 动作 σ + 优化器状态。**ONNX**：只有 actor 的九步（Sub, Div, 4×Gemm, 3×Elu），输出均值。
- ONNX 是跨框架的计算图文件，真机用 onnxruntime 跑，不需要 torch。
- numpy 手写九步 = onnxruntime，差异 1e-6。
- 部署**不采样**；归一化**必须烘进去**，漏掉会造成严重输出差异，具体幅度随模型与输入而变，仿真回放可能掩盖它。
- 真机循环：拼 61 维 → ONNX → HOME + μ → 4 小步物理，50 Hz；多个策略共用 61 维格式热切换。
