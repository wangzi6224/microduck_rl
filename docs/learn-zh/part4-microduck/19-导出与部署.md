## 19.0 先看地图：一份可以接着改的工程档案，一张只管照着做的菜谱卡

**训练结束会留下两个文件。一个装着"接着练所需要的一切"，另一个只装着"从 61 个数算到 14 个数的那一串步骤"。
前者给下一次训练，后者给机器人。这一章就是打开后者，一步一步看清里面是什么，并且亲手用加减乘除算一遍。**

打个比方。一家餐厅的后厨里有两样东西：

- **整间厨房**：食材、配方笔记、上次试菜的记录、厨师的经验、还没定下来的改法。要继续研发新菜，这些一样都不能少。
- **一张菜谱卡**：几克盐、油温几度、先下什么后下什么。拿着这张卡，一个没进过这间厨房的人也能把这道菜做出来。

`model_4.pt` 是整间厨房，导出的 `.onnx` 是那张菜谱卡。
真机上的程序只要那张卡：它不打算研发新菜，它只要每 0.02 秒照着做一遍。

## 19.1 两个文件：一个留着接着练，一个交给机器人

第 14 章 14.9 节已经打开过运行目录（一次训练把产物写进去的那个文件夹，`logs/rsl_rl/velocity/<日期时间>_learnzh-ch14/`）。那里有两样东西跟这一章有关：

```
                                 文件   字节数
-------------------------------------  -------
                           model_0.pt  4842943
                           model_4.pt  4842943
2026-09-22_13-21-10_learnzh-ch14.onnx   793706
```

（这是实验第 1 节打印的：左列是文件名，右列是文件大小，单位是字节。文件名带着训练开始的日期时间，**你的会不同**。
`model_0.pt` 和 `model_4.pt` 一样大：第 0 圈和第 4 圈存下的数一样多，只是数值不同。）

`model_N.pt` 这种文件叫**检查点**（checkpoint）：训练到第 N 圈时，把"接着练所需要的一切"原样存下来的一份存档（`.pt` 是 PyTorch 存文件常用的后缀）。
第 14 章 14.9 节数过里面的五样东西——actor、critic、Adam 的两本账、圈号、步数——这里不重数。
本章只用得上其中一样：`actor_state_dict`，也就是 actor 那张网的全部数：四层的权重和偏置、14 个动作 σ，还有归一化器攒下的平均和标准差（第 14 章 14.9 节）。

另一个文件的后缀是 `.onnx`。**ONNX**（Open Neural Network Exchange，"开放神经网络交换"）是一种**文件格式**。
"格式"就是"文件里的字节怎么排"的约定，和 `.json`、`.png` 一样：约定是公开的，谁都能写一个程序去读它。
ONNX 约定的是：把一张网络**要做哪几步计算**、以及**每一步要用到的那些固定不变的数**，一起存进一个文件。
存进去之后，任何认得这种格式的程序都能照着算——不需要 PyTorch，不需要 Python，不需要训练时的那套环境。

用前端的话说：检查点像整个项目目录（源码、`node_modules`、测试、git 历史），拿着它能接着开发；
ONNX 像 `npm run build` 打出来的那个 `.js` 文件——浏览器不用装 webpack 就能跑它，可你没法从它接着开发。

两个文件的分工，一句话说清：

| 文件 | 里面有什么 | 给谁用 |
|---|---|---|
| `model_N.pt` | 检查点：actor + critic + Adam 的两本账 + 圈号 + 步数 | 接着练、在仿真里回放 |
| `xxx.onnx` | 只有 actor 的那一串计算步骤（归一化已经烘在里面，第 8 章 8.6 节） | 交给机器人 |

大小对得上这个分工。上面表里是字节数，换成 MB 按一百万字节算（第 14 章 14.9 节量过这两个文件）：
检查点 4,842,943 ÷ 1,000,000 ≈ 4.8 MB，ONNX 793,706 ÷ 1,000,000 ≈ 0.79 MB；4,842,943 ÷ 793,706 ≈ 6.1，差不多 6 倍。

为什么偏偏是 6 倍左右？第 14 章 14.9 节按配置数过两边各装了多少个数，账可以粗算：

- critic 和 actor 差不多大（203,777 个旋钮对 197,788 个），两张网就是 **2 份** actor 那么多；
- Adam 给每个旋钮再记 m、v 两个数，旋钮加两本账，每一份变成 **3 份**；
- 2 × 3 = **6**。精确地数：(197,788 + 203,777) × 3 = 1,204,695 个数；ONNX 里是 197,896 个（19.3 节数），1,204,695 ÷ 197,896 ≈ 6.1。

ONNX 大约只是其中 1 份。多出来的 6 − 1 = 5 份——critic 1 份、actor 的两本账 2 份、critic 的两本账 2 份——全是**训练才需要、跑一步动作用不上**的东西。

> **停一下，自测**：同事只给了你一个 `.onnx`，没给检查点。下面三件事，哪些做得到？
> ① 在电脑上跑这个策略，看它对一帧观测给出什么动作；② 从他停下的那一圈接着往下练；③ 查出它训练时每一列用的是哪个平常值、哪个起伏。
> <details><summary>答案</summary>
>
> ① 做得到——文件里装的就是"怎么算"，谁认得这个格式谁就能照着算一遍。
> ③ 也做得到——归一化那两串数烘在文件里（第 8 章 8.6 节），19.3 节就把它们打印出来了（存的是 σ + 0.01，减掉 0.01 就是 σ）。
> ② 做不到：ONNX 里没有 critic（价值网络，第 10 章（价值函数）），没有 Adam 的两本账（第 7 章 7.5 节），没有 14 个动作 σ（第 4 章 4.7 节），也没有课程走到了第几档。

## 19.2 迷你版：3 个数进、2 个数出，自己导一个 ONNX 出来

真的那个文件有 61 个输入、197,774 个权重和偏置。直接打开它，看到的只会是一堆数。
所以先做一个**迷你版**：3 个数进去，2 个数出来，中间是**两层**：第一层 2 个神经元，过一道门；第二层再 2 个神经元。
神经元就是第 6 章 6.1 节的"一家店"：清单 × 价格表，加上运费，再过一道门。下面把第一层的两个神经元叫店 1、店 2。
（数层数就是数价格表：第 6 章 6.3 节把 61 → 512 → 256 → 128 → 14 数成四层，迷你版是 3 → 2 → 2，所以是两层。）
它和真的那个是同一种东西，只是每样都小到能用加减乘除算完。

迷你版的全部数字（都是为了好算而编出来的**教学构造数字**）：

- 三项读数的平常值 μ = (10, 0, 2)，起伏 σ = (1.99, 0.99, 3.99)：μ 是这一项训练时攒下的平均，σ 是它的标准差（第 8 章 8.3 节）。
  再加上第 8 章 8.3 节那个防止除以 0 的 ε = 0.01（一个固定的小数，不是第 4 章的随机噪声），分母 σ + ε 正好是整数：
  1.99 + 0.01 = **2**，0.99 + 0.01 = **1**，3.99 + 0.01 = **4**。σ 故意编成 1.99 这种数，就是为了这一步之后好手算。
- 第一层：店 1 的价格表是 (1, 0, 2)，运费 0.5；店 2 的是 (−1, 1, 0)，运费 −3。
  两张价格表上下摞起来，就是一张 2 行 3 列的表（第 6 章 6.2 节：行数 = 几家店，列数 = 清单有几项）。
- 第二层（输出层）两个神经元：第 1 个的价格表是 (2, 1)，运费 0；第 2 个是 (0, −1)，运费 1。摞起来是一张 2 行 2 列的表。

现在喂一帧读数 **(12, 2, 4)**，一步一步手算：

1. **减 μ、除以 σ + ε**（第 8 章 8.3 节）：(12 − 10) ÷ 2 = **1**；(2 − 0) ÷ 1 = **2**；(4 − 2) ÷ 4 = **0.5**。
   （第 1 项读到 12，比平常值 10 高 2，正好是 1 个起伏（σ + ε = 2），所以换算成 1。）
2. **第一层：价格表 × 清单 + 运费**（第 2 章 2.6 节）：
   店 1：1×1 + 0×2 + 2×0.5 + 0.5 = 1 + 0 + 1 + 0.5 = **2.5**；店 2：(−1)×1 + 1×2 + 0×0.5 − 3 = −1 + 2 + 0 − 3 = **−2**。
3. **过 ELU 门**（第 6 章 6.1 节）：正数原样过，所以 2.5 还是 2.5；负数 z 压成 $e^z - 1$，所以 $e^{-2} - 1 = 0.1353 - 1 = -0.8647$。
   （$e^{-2}$ 是第 1 章 1.8 节的指数函数：负 2 次方就是除两次 e，$e^{-2} = 1 ÷ e^2 = 1 ÷ 7.389 ≈ 0.1353$，
   第 1 章 1.8 节那张 $e^{-x}$ 表里 x = 2 那一格就是它；浏览器控制台里按 `Math.exp(-2)` 也能看到 0.1353…。）
4. **第二层**（最后一层，不过门——第 6 章 6.3 节：过了门，就给不出比 −1 更小的动作）：
   2 × 2.5 + 1 × (−0.8647) + 0 = 5 − 0.8647 = **4.1353**；0 × 2.5 + (−1) × (−0.8647) + 1 = 0.8647 + 1 = **1.8647**（负负得正）。

两个动作：**(4.1353, 1.8647)**。第 1 步其实是两小步（先减、再除），拆细了一共五步——后面会看到，ONNX 文件里正好是五个方框。

第 2 项的数字是特意挑的：它的 μ 是 0、分母是 1，所以 2 进去还是 2——**归一化对它什么也没做**，
另外两项各被改成了什么，一眼就能对照出来。别把它当摆设：第一层里店 1 给它的价格是 0（根本不看它），店 2 给的价格是 1（只有店 2 在看它）。
19.9 节把它和第 3 项对调一下，两个动作立刻就不是这两个数了。

这五步全都是加减乘除加一个 `Math.exp`，浏览器控制台里粘进去就能跑一遍：

```js
const norm = [(12 - 10) / 2, (2 - 0) / 1, (4 - 2) / 4];    // 减 μ、除以 σ+ε → (1, 2, 0.5)
const elu  = z => (z >= 0 ? z : Math.exp(z) - 1);          // 第 6 章 6.1 节那道门
const z1 =  1 * norm[0] + 0 * norm[1] + 2 * norm[2] + 0.5; // 第一层店 1 → 2.5
const z2 = -1 * norm[0] + 1 * norm[1] + 0 * norm[2] - 3;   // 第一层店 2 → −2
[2 * elu(z1) + 1 * elu(z2) + 0,  0 * elu(z1) - 1 * elu(z2) + 1];   // → [4.1353…, 1.8647…]
```

![四步讲迷你策略：读数12、2、4减去μ十、零、二再除以二、一、四得到1、2、0.5；第一层两家店算出2.5和−2；ELU门把−2压成e的−2次方减一等于−0.8647；第二层算出4.1353和1.8647，下面是Sub Div Gemm Elu Gemm五个方框](../figures/ch19_mini_graph.png)

**这样读图：** ①②③④ 竖着读，每一步的手算就写在图里，和上面正文里的数字是同一组。
蓝字是店 1 和第 1 个动作那一路，绿字是店 2 和第 2 个动作那一路。① 右边三个橙色格子是换算好的三个数；③ 只有 −0.8647 描成橙色，因为门只改了它（2.5 原样通过）。
图里的 `e^(−2)`、`e^z − 1`，就是 $e^{-2}$、$e^z - 1$：纯文字没法把指数写到右上角，就用 `^` 表示"的几次方"（JS 里写 `**`，第 1 章 1.8 节）。
最要紧的是 ④ 最下面那一排方框：这五步存进 ONNX 文件之后，就是**五个方框**，橙色的那个就是 ③ 那道门。
方框上那几个英文名字下一段就解释。

现在把这个迷你网络**真的导出成一个 ONNX 文件**，再打开它看。实验第 2 节干的就是这件事：先用 torch 搭出这台迷你网络，
再交给 torch 自带的**导出器**（把 torch 里的网络翻译成 ONNX 文件的那段程序，`torch.onnx.export`），最后打开导出的文件，打印出这三行：

```
迷你 ONNX 的算子 : Sub → Div → Gemm → Elu → Gemm
它存下来的常数   : fc1.weight [2, 3], fc1.bias [2], fc2.weight [2, 2], fc2.bias [2], _mean [1, 3], add [1, 3]
除法用的那个常数 : (2, 1, 4) = σ + ε，导出时就加好了，图里只有一次除法
```

文件里存的就两类东西：

- 一串**算子**（operator）：ONNX 把计算拆成一台台小机器，每台机器叫一个算子。
  `Sub` 是减法，`Div` 是除法，`Gemm` 是"矩阵乘一下再加个偏置"（第 2 章 2.6 节的价格表 + 运费），`Elu` 就是那道门。
  这正是第 7 章 7.1 节的计算图——那里我们把一行算式拆成小机器是为了往回传梯度，这里存下来是为了让别人照着往前算。
  用前端的话说，它像一个排好顺序的函数数组：照着算的程序把输入交给第一个函数，结果再交给下一个，
  就是 `ops.reduce((x, op) => op(x), obs)` 这一行。
- 一堆**常数**：每台机器要用到的、固定不变的数。价格表、运费、μ，还有那个 (2, 1, 4)。
  输出第二行就是它们，名字是 torch 起的：`fc1` 是第一层、`fc2` 是第二层（fc 是 fully connected"全连接"的缩写：每家店都看清单的全部项）；
  `.weight` 是价格表、`.bias` 是运费（第 2 章 2.6 节的权重和偏置）；`_mean` 是三个 μ，`add` 是三个 σ + ε。
  方括号里是形状（第 2 章 2.8 节）：`fc1.weight [2, 3]` 就是店 1、店 2 的价格表摞成的 2 行 3 列，2 × 3 = 6 个数。
  六个常数一共 6 + 2 + 4 + 2 + 3 + 3 = 20 个数：上面编的价格表、运费、μ 都在，σ 和 ε 合成了 3 个 σ + ε。

注意第三行：σ + ε 不是存两份再让运行时去加，而是**导出的时候就加好了**，文件里直接存 (2, 1, 4) 这一个常数。
σ 和 ε 都是定死的数，能提前算的就提前算好，每一帧就少做一次加法；所以图里只有一次除法。
（它在文件里的名字是 `add`——导出器按"这个数是怎么算出来的"随手起的名，不用管。）

| 符号 | 怎么读 | 就是 |
|---|---|---|
| `Sub` | "sub" | subtract，减法。这里是减 μ |
| `Div` | "div" | divide，除法。这里是除以 σ + ε |
| `Gemm` | "gem-m" | 矩阵乘 + 偏置 $W\mathbf{x}+\mathbf{b}$（第 2 章 2.6 节）。名字是 GEneral Matrix Multiply（通用矩阵乘）的缩写 |
| `Elu` | 按字母读 | 第 6 章 6.1 节那道门 |

对回上面的手算：`Sub`、`Div` 是第 1 步的"减 μ""除以 σ + ε"，第一个 `Gemm` 是第 2 步，`Elu` 是第 3 步，第二个 `Gemm` 是第 4 步——五个算子，一个萝卜一个坑。

拿这个文件跑一遍 (12, 2, 4)，和我们的手算并排（实验第 2 节原样打印）。
跑文件的是 onnxruntime：一个专门照着 ONNX 文件算的程序，19.3 节细说。
表的前五行是手算的五步（第一行是喂进去的读数），最后一行是 onnxruntime 交出来的两个动作：

```
                  这一步          算出来是
------------------------  ----------------
                读数 obs        (12, 2, 4)
         减 μ 再除以 σ+ε       (1, 2, 0.5)
 第一层（价格表 + 运费）         (2.5, −2)
               过 ELU 门    (2.5, −0.8647)
           第二层 = 输出  (4.1353, 1.8647)
onnxruntime 跑同一个文件  (4.1353, 1.8647)
```

最后两行一模一样（印到 4 位小数是这样；更靠后的末几位其实差一点点，19.4 节专门讲）。**你已经把一个 ONNX 文件从头到尾手算了一遍。**

> **停一下，自测**：同一个迷你策略，换一帧读数 (8, 1, 6)。归一化之后是多少？两个动作各是多少？
> （用得上 $e^{-1} = 0.3679$。）
> <details><summary>答案</summary>

> 第一层：1×(−1) + 0×1 + 2×1 + 0.5 = −1 + 0 + 2 + 0.5 = 1.5；(−1)×(−1) + 1×1 + 0×1 − 3 = 1 + 1 + 0 − 3 = −1。
> 过门：1.5 原样；ELU(−1) = 0.3679 − 1 = −0.6321。

## 19.3 打开真的那一个：九个算子，一步不多一步不少

迷你版是两层、中间夹 1 道门，5 个算子的账是：2 个归一化 + 2 个 `Gemm` + 1 个 `Elu` = 5。
真的那张网有四层（第 6 章 6.3 节：61 → 512 → 256 → 128 → 14），中间夹 3 道门（四层只有 3 道门：最后一层不过门，也是 6.3 节说的），照同一本账数：
2 个归一化 + 4 个 `Gemm` + 3 个 `Elu` = **9**。打开来看（实验第 3 节）：

```
输入 : obs [1, 61]
输出 : actions [1, 14]
算子 : Sub → Div → Gemm → Elu → Gemm → Elu → Gemm → Elu → Gemm
```

一个不多，一个不少。输入的名字叫 `obs`（observation，观测），形状 `[1, 61]`——第 2 章 2.8 节的写法：一次算 1 帧，每帧 61 个数。
输出叫 `actions`（动作），`[1, 14]`。前面那个 1 是一批里有几帧（第 2 章 2.7 节的批量：训练时 4096 只机器人的观测摞成 `[4096, 61]` 一起算）；
导出的文件把它固定成 1，因为真机只有一只机器人，一次只算一帧。

九个算子和前面几章一一对得上：第 8 章 8.3 节的归一化是两步；第 6 章 6.3 节那四行公式，每行先"乘价格表、加运费"（一个 `Gemm`），前三行再各过一道门（一个 `Elu`）。
下表第三列是这一步对手里的数做了什么，第四列是它在前面哪一章的哪一步：

| 第几个 | 算子 | 做什么 | 对应前面的哪一步 |
|---|---|---|---|
| 1 | `Sub` | 61 个读数，各减自己的平常值 | 第 8 章 8.3 节第 1 步：减平均 |
| 2 | `Div` | 再各除以自己的 σ + 0.01 | 第 8 章 8.3 节第 2 步：除以标准差 + ε |
| 3 | `Gemm` | 512 行 61 列的价格表乘清单，加 512 笔运费 | 第 6 章 6.3 节第 1 行的 $W_1\mathbf{x} + \mathbf{b}_1$ |
| 4 | `Elu` | 512 个数逐个过门 | 第 1 行外面那层 ELU，得到 $\mathbf{h}_1$ |
| 5、6 | `Gemm`、`Elu` | 256 行 512 列的表，再过门 | 第 2 行，得到 $\mathbf{h}_2$ |
| 7、8 | `Gemm`、`Elu` | 128 行 256 列的表，再过门 | 第 3 行，得到 $\mathbf{h}_3$ |
| 9 | `Gemm` | 14 行 128 列的表，不过门 | 第 4 行，得到 14 个动作 |

（第四列沿用第 6 章 6.3 节的写法：$W_1$ 是第 1 张价格表，$\mathbf{b}_1$ 是第 1 层的运费，$\mathbf{h}_1$ 是第 1 层过门后报出的那串数；字母写成粗体，表示它是一整串数。）

第 9 个算子吐出的 14 个数，就是第 4 章 4.7 节那 14 口钟的中心。部署时只用钟的中心（19.5 节），而它吐出来的已经是中心，
所以"只取中心"不用再多一个算子。19.4 节那五行 numpy，就是照这张表一行一行写的。

![两步图：上面九个算子Sub Div Gemm Elu Gemm Elu Gemm Elu Gemm排成一条流水线，标注Sub和Div是归一化、Gemm是价格表加运费、Elu是那道门；下面五根柱子高度严格按个数成比例，输入61、第1层512、第2层256、第3层128、输出14，图上注明512除以14约等于37所以最右边那根薄成一条线](../figures/ch19_nine_ops.png)

**这样读图：** ① 从左到右就是算的顺序，和上面那行输出一字不差；下面两行彩字是图例：蓝字说 Sub、Div 是归一化，绿字说 Gemm 是价格表 + 运费，橙字说 Elu 是那道门，最后一句是 2 + 4 + 3 = 9 的账。
② 柱子的高度和"这一步手里有多少个数"成比例：61 项观测先被第一层摊开成 512 个数，再一层层收回到 14 个。橙框的两根是两头（输入 61、输出 14），中间三根是三个隐藏层。
最右边那根 14 的柱子薄成了一条线——图里专门注了一句：512 ÷ 14 ≈ 37，最高那根是它的 37 倍，它本来就该这么薄，不是画漏了。

文件里存下来的常数（同样是实验第 3 节打印的）。三列是：常数的名字；形状（第 2 章 2.8 节：几行几列）；有几个数，也就是形状里的数相乘。
拿第二行手算：`[512, 61]` 是 512 行 61 列，512 × 61 = 31,232 个数——第 6 章 6.5 节那张旋钮表的第一格。`[1, 61]` 是 1 × 61 = 61 个。

```
 ONNX 里存下来的常数        形状  有几个数
--------------------  ----------  --------
obs_normalizer._mean     [1, 61]        61
        mlp.0.weight   [512, 61]     31232
          mlp.0.bias       [512]       512
        mlp.2.weight  [256, 512]    131072
          mlp.2.bias       [256]       256
        mlp.4.weight  [128, 256]     32768
          mlp.4.bias       [128]       128
        mlp.6.weight   [14, 128]      1792
          mlp.6.bias        [14]        14
        onnx::Div_24     [1, 61]        61
```

**怎么读这段输出**：中间八行是第 6 章 6.5 节数过的四张价格表和四串运费。`mlp` 是多层感知机（第 6 章 6.3 节）的缩写；
rsl_rl 把它存成一串零件，从 0 开始编号：0 号是第一张价格表，1 号是第一道门，2 号是第二张价格表……门没有要存的数，所以表里只看得到 0、2、4、6 四个号，`mlp.6` 是最后一层。
头一行和末一行是归一化那两个常数：`obs_normalizer` 是观测的归一化器（第 8 章），`_mean` 是它的 61 个平均 μ；末一行是 61 个"σ + 0.01"——和迷你版里那个 (2, 1, 4) 一样，加法在导出时就做完了，
名字 `onnx::Div_24` 是导出器自己编的。实验核对过：它**逐位等于**检查点里的 `obs_normalizer._std`（61 个标准差）加 0.01。

照着这个文件算的那个程序，叫**推理运行时**（inference runtime）。
"运行时"这个词前端很熟：一个 `.js` 文件自己不会跑，要交给 JavaScript 运行时（浏览器、Node.js）去执行，同一个文件 Chrome、Firefox、Node 都能跑。
`.onnx` 文件也一样，自己不会算，要交给一个推理运行时。
"推理"（inference）就是"只往前算一遍，不学习"：拿输入，走完这九步，交出输出，不碰任何一个权重。
本章用的是其中最常见的一个，叫 ONNX Runtime（代码和实验输出里写作 `onnxruntime`，19.2 节那张表的最后一行就是它算的）。
本仓库那个 CPU 排练脚本（19.7 节）用的就是它，它不需要 PyTorch。
真机那头装的是哪一个运行时，由另一个仓库说了算，**本书没有核实过**（19.10 节的折叠块再说一次）。

文件里还附了一小段**元数据**（metadata，就是"关于这个文件的说明"），8 项。它不参与计算，只是贴在文件上的标签——
像 `package.json` 里的 `name`、`version`，或者照片文件里记着的拍摄时间、相机型号。实验第 3 节打印了其中 4 项。
下表三列：元数据的名字、它记的是什么、对应前面哪一章：

| 元数据 | 是什么 | 对应哪一章 |
|---|---|---|
| `observation_names` | 61 项观测是哪 8 块、什么顺序 | 第 15 章 15.1 节 |
| `joint_names` | 14 个关节的名字和顺序 | 第 15 章 15.3 节 |
| `default_joint_pos` | 14 个 HOME 角度 | 第 17 章 17.1 节 |
| `action_scale` | 动作乘几倍变成角度（这里是 1.0） | 第 17 章 17.1 节 |

这四项就是第 15 章说的"约定"。真机那头拼观测、换算动作，都得按它们来。
（另外 4 项：`run_path` 记着它出自哪一次训练（wandb 上那次运行的名字，或者导出时用的检查点路径）；`command_names` 是命令块各格的名字；
`joint_stiffness` / `joint_damping` 是"硬度"和"阻尼"，给理想弹簧那种执行器用的两个参数（第 17 章 17.4 节说过项目为什么不用理想弹簧）。
项目用的是 BAM 执行器——第 17 章 17.4 节那只照着真舵机的实验拟合出来、自己从电压和摩擦算力矩的"虚拟舵机"——所以这两项读出来是 1 和 0，在这里没有意义。）

> ⚠️ **算子数对了，不等于导对了。** 九个算子是"这一次、用这个导出器"的结果。
> 换一个版本的导出器，可能把 `Sub` 和 `Div` 合成一个算子，也可能把 `Gemm` 写成别的等价形式——
> 那样数出来不是 9，网络却一点没变。**所以不要拿"算子个数"当验收标准**；该核对的是 19.4 节那件事：同样的输入，输出对不对得上。

> **停一下，自测**：上面那张常数表里，ONNX 一共存了多少个数？和第 14 章 14.9 节说的 197,774 差多少？差的是什么？
> <details><summary>答案</summary>
>
> 四张价格表和四串运费加起来 31232 + 512 + 131072 + 256 + 32768 + 128 + 1792 + 14 = 197,774，正是第 6 章 6.5 节数过的那个数。
> 再加上归一化的 61 个 μ 和 61 个 σ + 0.01（61 + 61 = 122 个），一共 197,774 + 122 = 197,896 个数。多出来的 122 个，就是被"烘"进文件里的归一化（第 8 章 8.6 节）。

## 19.4 手写 = ONNX：同样的观测，差在百万分之一上下

到这一步，一件事已经很清楚了：这九步你全都会算。那就不用任何框架，自己写一遍。
为什么要多此一举？手写版只知道这九步，别的什么也没有；它要是和 ONNX 算得一样，就说明那个文件里除了这九步，确实没藏别的东西。
实验第 4 节用 numpy（Python 里做数组计算的库）写的就是下面这五行。后四行第 6 章 6.6 节手写过，这里只在最前面多了一行归一化
（`W`、`B` 是从检查点里取出来的四张价格表和四串运费，`mean`、`std` 是那两串统计；脚本里 0.01 写成了变量 `EPS_HAND`，"改一改"第 3 条就是改它）：

```python
x = (obs - mean) / (std + 0.01)            # Sub、Div：第 8 章 8.3 节的归一化，ε = 0.01
h = elu(W[0] @ x + B[0])                   # Gemm + Elu：第一层 512 个神经元，过门
h = elu(W[1] @ h + B[1])                   # 第二层 256 个
h = elu(W[2] @ h + B[2])                   # 第三层 128 个
return W[3] @ h + B[3]                     # 最后一层 14 个，不过门：输出就是 14 个动作
```

（`@` 是 Python 里的矩阵乘号，`W[0] @ x` 就是第 2 章 2.6 节"512 行 61 列的价格表乘一张 61 项的清单"。）

喂 5 帧随便造的观测（每一项从一口中心 0、宽 0.5 的钟里随机抽，第 4 章 4.7 节那种抽法，大多落在 −1 到 1 之间），和 ONNX Runtime 的结果比最大差异：

```
                                    前 5 个动作（rad）
-----------  -----------------------------------------
 numpy 手写  [-0.0173  0.1113  0.4024 -0.669   0.753 ]
onnxruntime  [-0.0173  0.1113  0.4024 -0.669   0.753 ]
5 帧随机观测的最大差异 = 7.15e-07  （你的数字会不同；量级应该在 1e-6 上下）
```

表的两行，是两边对第一帧算出的 14 个动作里的前 5 个，印到 4 位小数，一模一样。
最后一行的"最大差异"：5 帧 × 14 个动作，两边逐个相减、去掉负号（取绝对值，第 4 章 4.4 节的 $\lvert c\rvert$），挑出最大的那一个。

`7.15e-07` 是第 3 章 3.6 节的科学计数法，这回指数是负的：$7.15 × 10^{-7}$（这里的 e 是"乘 10 的几次方"的缩写，不是 2.718）。
10 的负几次方，就是 1 除以几个 10：

| 写法 | 写成小数 | 读法 |
|---|---|---|
| $10^{-1}$ | 0.1 | 十分之一 |
| $10^{-3}$ | 0.001 | 千分之一 |
| $10^{-6}$ | 0.000001 | 百万分之一 |
| $10^{-7}$ | 0.0000001 | 千万分之一 |

规律是：负几次方，小数点后就有几位，那个 1 落在最后一位。所以 `7.15e-07` 就是把 7.15 的小数点往左挪 7 位，0.000000715；
`1e-6` 是 0.000001，就是标题里的"百万分之一"。

**你的数字会不同**：这几个动作是那次冒烟训练的权重算出来的，换个检查点就换一组数。
不会变的是**数量级**（输出里简称"量级"）——只看一个数大约是 10 的几次方，不管前面是 7.15 还是 2：差异落在 $10^{-7}$ 到 $10^{-6}$ 这一带。
差一个数量级，就是差 10 倍。

### 为什么会差一点点：小数只存得下 7 位左右

这一点点差异叫**浮点误差**（"浮点"是电脑存小数那套办法的名字）。第 6 章 6.6 节说过：电脑里每个小数只存有限的几位，torch 默认大约 7 位数字（这种存法叫 float32）；
ONNX 文件和 onnxruntime 用的也是它。存不下的部分要四舍五入，误差就从这里来。

迷你版上就看得见。19.2 节第一个动作的精确值是 $2 × 2.5 + (e^{-2} - 1) = 5 + e^{-2} - 1 = 4 + e^{-2} = 4.135335283…$；
onnxruntime 交出来的是 4.135335445…，正是 float32 里离 4.135335283 最近的那个数。从头数，前 7 位数字都是 4.135335，从第 8 位起不同了：
4.135335445 − 4.135335283 = 0.000000162，也就是 $1.62 × 10^{-7}$。
浏览器控制台里按 `Math.fround(4 + Math.exp(-2))` 就能看到 4.135335445…（`Math.fround` 的意思是"按 float32 存一次，再取出来"）。

一次舍入只差这么一点。可一帧要做多少次乘法？四张价格表的每一格各乘一次：31,232 + 131,072 + 32,768 + 1,792 = 196,864 次，将近 20 万次，每一次的结果都要舍入。
两边算的是同一件事，但各有各的算法——比如为了快，把一长串加法拆成几段同时算、最后再合起来——加的顺序不一样，舍入就落在不同的地方。
顺序为什么会影响结果？JS 的数能存 16 位左右，在控制台里照样看得到：

```js
(0.1 + 0.2) + 0.3;   // 0.6000000000000001
0.1 + (0.2 + 0.3);   // 0.6：同样三个数，换个顺序加，末位就不一样了
```

这些舍入有大有小、有正有负，20 万次累积下来，最后的 14 个动作在小数点后第 6、7 位上对不齐——就是上面量到的 7.15e-07。
所以核对的办法是"最大绝对误差小于某个容差"，**不要求每一位都一样**——那个要求任何两套实现都过不了。

> ⚠️ **别用"完全相等"当验收条件。** $10^{-6}$ 和 19.6 节那种 1 rad 上下的错，差着六个数量级：1 ÷ 0.000001 = 1,000,000，六个 10 连乘——不会认错。
> 真正该定的是容差（差多少以内算通过）。14 个动作的单位是 rad，取 $10^{-4}$ 已经非常宽松了：
> 0.0001 rad × 57.3 ≈ 0.006°（1 rad ≈ 57.3°，第 15 章 15.1 节）。它比浮点误差（$10^{-6}$）大 100 倍，留足了余量；本身又仍是一个小到可以忽略的角度。

## 19.5 部署不采样：同一帧喂两次，输出一模一样

第 4 章 4.7 节说过：训练时，策略吐出的不是一个动作，是一口钟——真正执行的动作 = μ + σ × 噪声。
那颗随机的骰子是为了探索（第 9 章 9.4 节）：不试试没试过的动作，就不知道有没有更好的。

真机上不需要探索，需要的是**确定**：同样的处境，给同样的动作。所以部署时**只用 μ**，那颗骰子根本不掷。

拿迷你版的第一个动作比一比。假设训练时它那口钟的宽度 σ = 1（教学构造的数），中心就是网络算出的 4.1353。
同一帧喂两次，抽到的噪声一次是 0.5、一次是 −1.2，执行的动作就是 4.1353 + 1 × 0.5 = 4.6353 和 4.1353 + 1 × (−1.2) = 2.9353——两次不一样。
部署时两次都是 4.1353。

> ⚠️ **这一节的 μ 和 σ，不是 19.2 节那两个。** 名字撞了，装的东西完全不同。
> 19.2–19.4、19.6 里的 μ 和 σ 是**观测**那边的：每一项读数各有一个平常值、一个起伏（真模型是两串各 61 个数，迷你版是各 3 个），
> 用在流水线最前面那两步（`Sub`、`Div`）。这一节的 μ 和 σ 是**动作**那边的：14 个动作各有一个中心、一个宽度，
> 两串各 14 个数，用在最后一步之后（第 4 章 4.7 节）。一个在流水线的头上，一个在尾巴外面——
> 导出时前者被烘进文件，后者被丢掉。

这件事不用靠"运行时记得别加噪声"来保证，而是**导出时就做掉了**。看实验第 5 节：

- 同一帧观测喂两次，两次输出**逐位相同**：每一位小数都一样，连 19.4 节那种末位的差别都没有。要是文件里还在抽噪声，两次几乎不可能这样。
- ONNX 存下来的常数名字里，根本**没有** `std_param`（第 6 章 6.5 节：代码里给那 14 个动作 σ 起的名字）——它们留在检查点里，导出时丢掉了。

丢掉之后，运行时连"要不要加噪声"这个选择都没有。这就是兑现第 4 章 4.7 节和第 9 章 9.4 节留的那句话：部署到真机不再加噪声，直接执行钟的中心。

> **停一下，自测**：同事说"真机上也加一点噪声吧，抖一抖说不定更稳"。有什么问题？
> <details><summary>答案</summary>
>
> 至少两个。第一，噪声是用来试新动作的，试出来的好坏要靠奖励反馈回去改旋钮——真机上没有这个回路，试了也学不到，白抖。
> 第二，行为变得不可重复：同一段视频拍两遍不一样，出了问题没法复现，也没法说清"到底是策略的问题还是这次抖歪了"。
> 训练时的 σ 是拿来探索的，不是拿来当"鲁棒性"用的。
>
> </details>

## 19.6 忘了烘焙：同一帧读数，动作从 4.14 变成 40

第 8 章 8.6 节讲过**烘焙**：归一化器和网络装进同一个文件，真机程序只管交原始观测。
那一节拿一列读数算过：读数 6 本该换算成 0.9975 再交给网络，漏了归一化，网络看到的就是 6；而且漏掉归一化，程序一句错都不会报。
现在我们手里有一个能手算的迷你版，可以把"到底错多少"一路算到动作上。（标题里的 4.14，是 4.1353 保留两位小数。）

还是那帧 (12, 2, 4)。这回跳过 `Sub` 和 `Div`，把原始读数直接塞进第一层：

- 店 1：1×12 + 0×2 + 2×4 + 0.5 = 12 + 0 + 8 + 0.5 = **20.5**（本来是 2.5）。
- 店 2：(−1)×12 + 1×2 + 0×4 − 3 = −12 + 2 + 0 − 3 = **−13**（本来是 −2）。
- 过门：20.5 原样；ELU(−13) = $e^{-13} - 1$。$e^{-13}$ 是 1 连除 13 次 e，小到 0.0000023 左右（控制台 `Math.exp(-13)`），
  四舍五入到 6 位小数是 0.000002；所以 ELU(−13) = 0.000002 − 1 = −0.999998，四舍五入到 4 位就是 −1（门的下限，第 6 章 6.1 节）。
- 输出：2 × 20.5 + 1 × (−0.999998) = 41 − 0.999998 = **40.000002**；(−1) × (−0.999998) + 1 = 0.999998 + 1 = **1.999998**。
  （下面那张表四舍五入到 4 位，所以印成 40 和 2。）

实验第 6 节把两条路并排打印。三列是：哪一步、走归一化的那条路（就是 19.2 节）、跳过归一化的这条路：

```
    迷你版这一步          走归一化   跳过归一化
----------------  ----------------  -----------
进第一层的三个数       (1, 2, 0.5)   (12, 2, 4)
    第一层算出来         (2.5, −2)  (20.5, −13)
       过 ELU 门    (2.5, −0.8647)   (20.5, −1)
     输出（rad）  (4.1353, 1.8647)      (40, 2)
```

第一个动作从 4.1353 rad 变成 40 rad，**差 40 − 4.1353 = 35.8647 rad**。
动作的单位是 rad（第 15 章 15.1 节：1 rad = 180° ÷ π ≈ 57.3°），35.8647 × 57.3 ≈ **2055°**；
2055 ÷ 360 ≈ 5.7，差不多要转六圈。

### 这笔账拆开看：35.8647 差在哪

两条路只差在进第一层的三个数：(1, 2, 0.5) 换成了 (12, 2, 4)。顺着往下追：

1. **店 1**：三项的贡献原来是 1×1 = 1、0×2 = 0、2×0.5 = 1，现在是 1×12 = 12、0×2 = 0、2×4 = 8。
   多出 (12 − 1) + (8 − 1) = 11 + 7 = 18，所以 2.5 + 18 = 20.5。
2. **店 2**：同样被放大，从 −2 变成 −13。可它是负数，门会把负数压在 −1 以上，所以过门后只从 −0.8647 变到 −1，少了 0.1353。
3. **第一个动作** = 2 × 店 1 + 1 × 店 2。店 1 那份从 2 × 2.5 = 5 变成 2 × 20.5 = 41，多 36；店 2 那份少 0.1353。
   合起来 36 − 0.1353 = **35.8647**，正是上面那个差。

大头在店 1：它是正数，门不管，读数被放大的那一截原样传了下去，到第二层又乘了 2。
店 2 的错被门挡掉了大半，但这只是碰巧——换一帧读数，被放大的也可能正好落在正数那边。

![三步图：第一步读数12、2、4先过Sub和Div变成1、2、0.5再进网络，输出4.1353；第二步跳过Sub和Div，原始的12、2、4直接进网络，输出40；第三步两根横条画在同一把从0到40弧度的尺子上，短的4.1353、长的40](../figures/ch19_bake_or_not.png)

**这样读图：** ① 是正确的那条路，② 是漏了那两步的路——两张图里进网络的三个数不一样（② 里描橙色的格子，就是没换算过的原始读数），别的一模一样。
③ 把两个动作画在同一把尺子上（刻度是 rad），蓝条 4.1353、橙条 40：一眼能看出这不是"差一点"，是"完全不是一回事"。
图下那句里的"限位"，是关节在机械上能转到的最远处，再往外就被结构挡住了（第 17 章 17.1 节）。

真模型上没有迷你版这么夸张，但也在"整 rad"这一档。实验第 6 节用那个冒烟训练的检查点跑了一帧，最大差 1.9 rad 左右（1.9 × 57.3 ≈ 109°；**你的数字会不同**，取决于是哪一帧、哪个检查点）——
重点不是这个数，是它和 19.4 节那个 $10^{-6}$ **差着六个数量级**：1 rad 是 0.000001 rad 的 100 万倍。

第 8 章 8.6 节的那句话在这里就有了具体的分量：这种错**在仿真里回放看不出来**（回放：在仿真里把训练好的策略跑给人看，第 8 章 8.5 节），因为回放脚本用的是训练框架里的整个策略模型，归一化器本来就在里面。
所以仓库的规矩是：导出只走 `scripts/export.py` 这一条路，永远不要手工把检查点转成 ONNX。

## 19.7 真机的一圈：每 0.02 秒，读一次、算一次、追 4 小步

前面都在看这个文件里有什么。这一节看它**什么时候被用**。

本仓库里有一个 CPU 上的**部署排练**脚本 `scripts/infer_policy.py`：不用 GPU（显卡，训练时同时算 4096 只机器人靠它），
在普通电脑的 CPU 上用 MuJoCo（第 17 章 17.4 节的物理引擎）按真机的做法跑 ONNX，上真机之前先在这里排练一遍。
它的主循环（程序里一直重复的那一圈）每 0.02 秒转一圈（第 14 章 14.1 节的"环境步"那只钟）。
用前端的话说，像 `setInterval(loop, 20)`：0.02 秒 = 0.02 × 1000 = 20 毫秒，每 20 毫秒调用一次 `loop`。一圈做五件事：

```text
每 0.02 s：
  ① 读传感器，按第 15 章的顺序拼成 61 个数
  ② 把这 61 个数交给 ONNX，拿回 14 个数
  ③ 目标角 = HOME + 动作 × 1.0（第 17 章 17.1 节）；排练脚本还可以打开一个延迟缓冲（第 17 章 17.5 节）
  ④ 物理往前走 4 小步，每小步 0.005 s，舵机一直在追这个目标角
  ⑤ 把这 14 个数记成"上一步动作"，回到 ①
```

换算一遍：一圈 0.02 秒，一秒钟就转 1 ÷ 0.02 = 50 圈，写作 50 Hz（Hz 读"赫兹"，就是"每秒几次"，第 9 章 9.8 节）。
④ 的 4 小步各 0.005 秒（5 毫秒），4 × 0.005 = 0.02，正好一圈。物理为什么要切成小步？第 14 章 14.1 节说过：
物理一步算得太粗，脚会一下子"穿进"地面；做决定却用不着那么勤，0.02 秒一次就够了。

这五步里，有三处要和前面几章对上：

- **③ 少了一项偏置。** 第 17 章 17.1 节的公式是 HOME + 动作 × scale − 偏置。那个"− 偏置"是训练时的仿真替真机模拟编码器的那把歪尺子；
  真机的舵机自己就拿着这把歪尺子，排练脚本的仿真里又没有偏置，所以这里只算 HOME + 动作 × 1.0。
- **③ 的延迟缓冲数的是环境步。** 排练脚本的 `--delay 3 6` 是晚 3 × 20 = 60 到 6 × 20 = 120 毫秒，
  不是训练时那 3–6 个物理步（3 × 5 = 15 到 6 × 5 = 30 毫秒）。这正是第 17 章 17.5 节那条 ⚠️："延迟 3 步"，先问是哪只钟。
- **④ 是排练脚本里才有的小步。** 真实世界是连续的，没有"物理步"：真机上，舵机在这 0.02 秒里一直在追目标角。
  "4 个 0.005 秒的小步"是仿真（训练时和排练时都一样）用来近似这段连续时间的办法。
  ①②③⑤ 则是这个策略对真机程序的要求——观测要这样拼、动作要这样换算、上一步动作要这样记——真机那头也得照做。

![两步图：上面一圈五步，读传感器拼61个数、交给ONNX拿回14个数、HOME加动作等于目标角、物理走4小步、记成上一步动作，最后一步有箭头绕回第一步；下面一根时间条分成四段各0.005秒，合起来0.02秒等于50赫兹，策略只在开头算一次](../figures/ch19_deploy_loop.png)

**这样读图：** ① 的五个框按顺序走，⑤ 之后回到 ①，一秒钟转 1 ÷ 0.02 = 50 圈。
橙色那个框（②）就是这一章的文件被用到的地方——一圈只用一次。
② 那根时间条说明：这 0.02 s 被物理引擎切成 4 小步（每格 0.005 s），但**策略只在开头说一次话**，这 0.02 s 里目标角不变，舵机一直在追它。

实验第 7 节把这一圈的 ②③ 两步做了一遍：从元数据里取出 14 个 HOME 和 `action_scale`，
拼一帧 61 维（只在命令块的前 3 项填上"前进 0.2 m/s、左转 0.5 rad/s"，其余 58 项全填 0——这只是演示怎么拼、怎么换算，不是一帧真实的读数），
跑一次 ONNX，再算出 14 个目标角。

⑤ 那一步容易被忽略：交出去的 14 个数，下一圈要作为"上一步动作"塞回观测里
（第 15 章 15.3 节的那一块：清单里的 [34, 48)，排在 3 + 3 + 14 + 14 = 34 项之后的 14 项）。
真机程序自己得记着——ONNX 不替你记，它里面没有任何"上一次是什么"的记忆。

**命令块由人来填。** 61 项里最后 13 项是命令（第 15 章 15.5 节），13 = 3（速度）+ 4（头）+ 6（身体）。
走路时前 3 项是遥控器的速度指令，头部 4 项说头朝哪，身体 6 项走路用不上。
而 Microduck 上不止一个策略：走路、坐下起立、前滚翻各是一个单独的 ONNX。
它们共用同一个 61 进 14 出的接口，所以运行时按一下按钮就能换一个文件——这就是第 15 章 15.6 节说的热切换（开着机、不停下就换，和前端热更新是同一个"热"），
第 15 章 15.7 节的零填充（用不上的格子也必须占着）就是为了它。

![两步图：上面三个ONNX文件走路walk、坐下起立sitstand、前滚翻roulade都连到运行时，运行时一次只装一个，出来14个动作；下面13格命令块，走路用速度3格vx vy ωz和头部4格，坐下起立用第1格和头部4格，前滚翻一格都不用，第1格被橙色虚线框出来表示同一格在两个策略里意思不同](../figures/ch19_hotswap.png)

**这样读图：** ① 三个文件长得一样（61 进、14 出），所以能互换；运行时一次只装一个。
② 是同一个 13 格的命令块：表头 vx、vy、ωz 是速度 3 格，头1–头4 是头部 4 格，身1–身6 是身体 6 格；
三行分别是三个策略**训练时**怎么用它的，上了色的格子就是这个策略训练时有意义的格子：
走路用速度 3 格和头部 4 格，坐下起立用第 1 格和头部 4 格，前滚翻一格都不用。橙色虚线框起来的是**同一格**——
走路读作 `vx`，坐下起立读作姿态标志，这就是下面那条 ⚠️ 说的事。没上色的格子是零填充，位置必须占着，不然后面的块全会错位。
（零填充的格子里训练时填什么，各策略不一样：有的在 0 附近很小的范围里随机抽，比如走路的身体 6 格（第 15 章 15.7 节）、前滚翻的速度 3 格；
有的就是真的 0，比如坐下起立的身体 6 格、前滚翻的头部和身体 10 格。）

> ⚠️ **"全零"不是"什么都不做"。** 坐下起立那个策略把姿态标志放在命令块的**第 1 格**——
> 就是走路策略读作 `vx`（前进多快）的那一格。同一格，两种读法：走路那边填 0 是"别往前走"；
> 坐下起立那边 **1 是坐下、0 是站起**，填 0 是"给我站着"。
> 要命的地方在于，**全零恰好是命令块最自然的默认值**：遥控器还没接、按钮还没按、程序刚初始化，这 13 格就都是 0。
> 于是默认状态下，坐下起立那个策略一直在收到"站着"这条指令，机器人站得好好的一动不动——
> 看起来就像"按了按钮，策略不理我"，而它其实每一步都在认真执行你真正下达的那条命令。
> 形状一样、长度一样，任何"维数对不对"的检查都会通过（第 15 章 15.6 节那条 ⚠️ 说的就是这件事）；
> 错的是**这一格是什么意思**。所以热切换换的不只是文件，还得换上这个策略自己的命令约定。

> **停一下，自测**：按了"坐下"的按钮，机器人纹丝不动。手边有 ONNX 文件、有排练脚本。你先查哪两件事？
> <details><summary>答案</summary>
>
> 第一，运行时到底装上那个策略的文件了没有（是不是还在跑走路那个）。
> 第二，命令块第 1 格填进去的是什么——按钮有没有把它从 0 改成 1。
> 这两件事都跟网络的权重无关。重新训练一个网络不会有任何帮助：它从来就没收到过"换姿态"这个输入。
>
> </details>

读到这里，从"训练存下一个检查点"到"机器人每 0.02 秒动一次"的整条路已经走完了。
剩下三节讲的是**出问题时怎么分辨**，第一遍累了可以先跳到 📍 和本章小结。

## 19.8 它是一张菜谱卡：每次现算，不是播放一段录好的动作

有一个很自然的误会，值得单独说一句：**导出的不是一段动作录像。**

检查点像一份还能接着改的工程档案；ONNX 像一个打包好的函数——
可它仍然是个**函数**（第 1 章 1.1 节：一台机器，喂进去什么就吐出对应的结果；第 6 章 6.6 节：actor 就是吃进 61 个数、吐出 14 个数的那台机器）：
每次拿当前这一帧观测，现场算出一组新动作。它不是把训练时录下的 14 个角度按顺序播放一遍。

用前端的话说，它是一个**纯函数**：同样的参数永远返回同样的结果，自己不偷偷记任何状态——"上一步动作"得由调用它的程序记着（19.7 节第 ⑤ 步）。
录像则像一张 `.gif`：不管页面上发生什么，它都只按顺序放那几帧。

还是那个迷你版，两帧不同的读数（实验第 8 节）。表的第一列是喂进去的读数，后四列就是 19.2 节手算的那四步：

| 喂进去的三个读数 | 归一化后 | 第一层 | 过门后 | 输出 |
|---|---|---|---|---|
| (12, 2, 4) | (1, 2, 0.5) | (2.5, −2) | (2.5, −0.8647) | **(4.1353, 1.8647)** |
| (10, 0, 2) | (0, 0, 0) | (0.5, −3) | (0.5, −0.9502) | **(0.0498, 1.9502)** |

第二帧三个读数正好等于 μ，归一化之后全是 0，于是第一层只剩下运费 (0.5, −3)；
过门后 $e^{-3} - 1 = 0.0498 - 1 = -0.9502$（$e^{-3} = 1 ÷ e^3 = 1 ÷ 20.09 ≈ 0.0498$，$e^3 = e × e × e ≈ 20.09$）；
输出 2 × 0.5 + (−0.9502) = 1 − 0.9502 = **0.0498**，和 (−1) × (−0.9502) + 1 = 0.9502 + 1 = **1.9502**。

同一个文件，两帧不同的观测，两组完全不同的动作。反过来，**同一帧连着喂两次，输出一模一样**（19.5 节）。
这两句话合起来，正好说清了"确定"的含义：**输出完全由这一帧输入决定**。
它不等于"机器人每次都走同一条路"——真实的传感器读数和物理状态，每一次都不一样。

<details>
<summary>进阶：这个文件的边界在哪里（现在可跳过）</summary>

ONNX 里有的：归一化的 μ 和 σ + ε，四张价格表，四串运费。就这些。

ONNX 里**没有**的：仿真环境、奖励函数、GAE（第 12 章的优势估计）、critic、Adam、课程——训练那一整套（第 3 部和第 4 部讲的东西）一样都没进来。
还少三样容易被想当然的：14 个动作 σ（第 4 章 4.7 节）、"上一步动作是什么"的记忆、以及"把 14 个数换算成关节角"这一步。

最后一条特别容易搞错：元数据里确实写着 HOME 和 `action_scale`（19.3 节），但那只是**写在说明里**，
不等于 ONNX 的输出已经是绝对角度了。它的输出仍然是"比 HOME 多转多少"，换算是**运行时**做的（19.7 节第 ③ 步）。
"文件里记了这个字段"和"文件替你做了这件事"，是两回事。

</details>

## 19.9 三种差异：先看差多少，再猜是哪一种毛病

两头的数对不上，先别急着改网络——**先量一量差多少**。差多少这件事，本身就把毛病分成了几类。
拿迷你版把三种情况各算一遍（实验第 9 节），数量级差得很远。表的第二列是"第 1 个动作和正确的 4.1353 差多少"（取绝对值），第三列是一句话的原因：

```
                       哪种问题  第 1 个动作差多少（rad）                          怎么回事
-------------------------------  ------------------------  --------------------------------
浮点误差（手写 vs onnxruntime）                     2e-07          算的是同一件事，末位不同
         把读数的第 2、3 项对调                    1.1353         形状还是 3 项，意思全变了
                     漏掉归一化                   35.8647  网络看到的数完全不是训练时的量级
```

三行都是迷你版上的数。第一行那个 2e-07（= 0.0000002）是迷你版自己的浮点误差，就是 19.4 节算过的那个 0.000000162，四舍五入成了 0.0000002；
它和 19.4 节真模型那次 7.15e-07 不是同一次比较，但都在 $10^{-7}$ 这一档。

中间那行是新的，手算一遍：把读数的第 2、3 项对调，(12, 2, 4) 变成 (12, 4, 2)——
这模拟的是"两头约定不一致"，比如拼观测的顺序和训练时不一样（第 15 章 15.6 节那个把 vx 和 ωz 填反的例子）。

- 归一化：(12 − 10) ÷ 2 = 1；(4 − 0) ÷ 1 = **4**；(2 − 2) ÷ 4 = **0**。
- 第一层：1×1 + 0×4 + 2×0 + 0.5 = 1 + 0 + 0 + 0.5 = **1.5**；(−1)×1 + 1×4 + 0×0 − 3 = −1 + 4 + 0 − 3 = **0**。
- 过门：1.5 原样；ELU(0) = 0（0 不是负数，门不管它）。
- 输出：2 × 1.5 + 1 × 0 = **3**；(−1) × 0 + 1 = **1**。

从 4.1353 变成 3，差 **1.1353 rad**（1.1353 × 57.3 ≈ 65°）。形状还是 3 项，一点错都没报，动作却不是那个动作了。

三种毛病，三种查法。下表第一列是你量到的差（第 1 个动作，或者 14 个动作里差得最多的那个），第二列是这一档最常见的原因，第三列是下一步该做什么：

| 差多少 | 多半是什么 | 怎么办 |
|---|---|---|
| $10^{-7}$–$10^{-6}$ | 浮点误差 | 正常，定个容差就行（19.4 节） |
| 零点几到几 rad，但形状全对 | 顺序、单位、坐标系或者命令格子的意思对不上 | 拿元数据逐块核对（19.3 节），别动网络 |
| 一大片都对不上，量级明显不对 | 漏了或者多做了归一化 | 检查从传感器到网络这条路上恰好做了一次（第 8 章 8.6 节） |

后两行在真模型上可能挨得很近：19.6 节真模型漏掉归一化，最大也只差 1.9 rad 左右，落进了第二行的"零点几到几 rad"。
所以分辨后两行，不能只看动作差多少，还要看**喂进网络的那 61 个数**：漏了或多做了归一化，是 61 项整体换了一套刻度
（第 8 章 8.6 节那一列：读数 6 该变成 0.9975，漏了就是 6，多做一次成了 −0.25）；格子填错，只有填错的那几项不对，其余各项都正常。

中间那一行最值得记住：**这种毛病重新训练一个网络是治不好的**。重新训练是在仿真里练，仿真那头的格子一直是按约定填的；
网络练得再好，真机这头喂进去的仍然是填错的数。

## 19.10 证据分四种：跑得起来、数值一致、接口一致、行为达标

最后一节不讲计算，讲一件更朴素的事：说"这个策略能用"之前，手里该有哪几样东西。

**第一件：说清楚这个 ONNX 是从哪来的。** 任务 ID（训练时 `uv run train` 后面跟的那个任务名）、哪一次训练（哪个运行目录）、第几个检查点。
听起来像废话，可目录里常常躺着好几个 `.onnx` 和好几个 `model_*.pt`，"挑最新的两个"并不保证它们是一对——
手工导过几次的目录尤其容易配错。这件事可以**直接验**：把 ONNX 里存的第一层价格表，和每个检查点里的第一层价格表逐位比一比（实验第 10 节）：

```
    检查点  和 ONNX 第一层权重的最大差      结论
----------  --------------------------  --------
model_0.pt                   8.830e-03  不是这个
model_4.pt                   0.000e+00      配对
```

第二列是两张 512 行 61 列的第一层价格表逐格相减、去掉负号，再挑出最大的那一格。
`8.830e-03` 是 $8.830 × 10^{-3}$ = 0.00883（小数点往左挪 3 位）；`0.000e+00` 是 $0 × 10^{0}$ = 0（e+00 是"乘 10 的 0 次方"，也就是乘 1）。

差 0，就是同一组权重；差 0.0088，就不是（**你的数字会不同**，但"配对的那个差 0"不会变）。
model_0 和它差得不多，是因为 model_0 是第 0 圈练完存的，之后又练了 4 圈、拧了 4 × 20 = 80 次旋钮（第 14 章 14.3 节：每圈拧 20 次），权重只挪了一点点。
第 14 章 14.9 节说过，每存一次检查点就顺手导一次 ONNX，同名覆盖，所以目录里的 `.onnx` 对应的是**编号最大**的那个检查点。

**第二件：分清四种证据。** 下面四句话听起来都像"它行"，其实是四个不同的判断。
表的第一列是你想说的那句话；第二列是说这句话之前，手里必须有的证据；第三列是这句话还证明不了、得靠下一行去补的事。
从上往下，一行比一行难拿到：

| 你能说的话 | 靠什么证据 | 它**不能**替代的 |
|---|---|---|
| "导得出来、跑得起来" | 文件能加载，形状是 61 进 14 出 | 数值对不对 |
| "数值和训练那头一致" | 19.4 节那种最大误差 + 容差 | 两头对这 61 个数的理解一致 |
| "接口含义一致" | 用元数据逐块核对顺序、单位、HOME、命令格子 | 机器人真能站住、能走 |
| "在测试场景里能走 20 秒" | 仿真回放或真机录像，写清命令、出生姿态、时长、失败现象 | 换个场地、换块电池还能不能走 |

（"20 秒"只是举例，正好是训练时一个回合的最长时间，第 14 章 14.1 节；"出生姿态"是一回合开始时机器人摆的姿势。）

**这四层，拿迷你版当场演一遍。** 把 19.9 节那个错误放进这张表：读数本该是 (12, 2, 4)，运行时拼成了 (12, 4, 2)。
下表第二列是对调之后，这一层的检查会看到什么；第三列是这一层过不过：

| 这一层 | 对调之后怎么样 | 结论 |
|---|---|---|
| 跑得起来 | 还是 3 个数进、2 个数出，文件照样加载、照样吐出两个动作 | 过 |
| 数值一致 | 手写和 onnxruntime 喂的是同一组（已经填错的）数，两边都算出 (3, 1)，**差 0**——连浮点误差都没有 | 过 |
| 接口含义一致 | 拿元数据逐项核对顺序，才看出第 2、3 项反了：第一个动作 4.1353 → 3，差 1.1353 rad ≈ 65° | 不过 |
| 行为达标 | 命令的意思从头就错了，机器人不会做你要它做的那件事 | 不过 |

前两层满分，第三层才亮红灯。注意第二层那个 0：**数值那一层越干净，越说明不了接口对不对**——
它比的只是"两边照同一张图算出来的数一样不一样"，那张图错没错，它一个字也没说。（实验第 9 节把这个 0 也锁住了。）

上一行通过，不能替代下一行。19.7 节那个 CPU 排练脚本也一样：它是**部署路径**的检查工具，里面仍然是仿真，不等于真机验证过了。
按这个层次记录，出了问题才分得清是训练、是转换、是运行时的理解，还是真实物理的差别。

<details>
<summary>进阶：再往后——把策略发布出去（现在可跳过）</summary>

仓库里有一条 `uv run publish` 命令，把 `policy.onnx` 连同一份说明文件（manifest）打包传到 Hugging Face Hub 上（一个专门放模型文件的网站，像放代码的 GitHub）。
说明文件里写的就是上面那些约定，本仓库 `src/mjlab_microduck/publish/manifest.py` 里能查到这几个定死的数：
`SCHEMA_VERSION = 2`（说明文件的版本）、`MODEL_API = 1`、`OBS_LEN = 61`、`ACTION_LEN = 14`，
机器人型号那一项里还写着 `control_hz: 50`（19.7 节那只钟）。实验第 11 节核对这几行还在不在。

真机那头由另一个仓库（`pollen-robotics/microduck`）里的守护进程（一直在后台跑着的程序）去拉取和加载，本书**没有核实过**那部分代码。
要记住的只有一句：**发布是一个分发动作**，把文件搬到另一台机器上；它不会让策略变好一点点。

</details>

> **停一下，自测**：有人说"ONNX 输入维数是 61、随机输入下和训练那头的输出一致，sim2real 成功了"（sim2real：从仿真 simulation 搬到真机 real）。这话哪里不对？
> <details><summary>答案</summary>
>
> 它只证明了**这些输入上的数值转换一致**（上表第二行）。还差三件事：
> 两头对这 61 个数的理解是不是一致（顺序、单位、坐标系、命令格子的意思，19.9 节）；
> 随机造的输入并不是真实观测，真机上的读数不一定落在训练见过的范围里；
> 以及最后——机器人到底站不站得住。四种证据，它拿到了一种。
>
> </details>

## 📍 映射到项目

同一个文件的说明里写着烘焙为什么是自动的（第 8 章 8.6 节、19.6 节）：

> `runner.export_policy_to_onnx` emits `actor(normalizer(obs))`, so what the robot runs is what training saw.
>
> （大意：导出的图算的是"先归一化、再过 actor"，所以机器人跑的就是训练时网络看到的那一套。）

**被导出的到底是哪个模块**：`rsl_rl/models/mlp_model.py` 里的 `_OnnxMLPModel`，它的 `forward` 只有三行——
这三行就是 19.3 节那九个算子的来历：

```python

    out = self.mlp(x)                       # 4 个 Gemm + 3 个 Elu：四层网络（第 6 章 6.3 节）

```

**真机排练**：`scripts/infer_policy.py` 的主循环，19.7 节那一圈：

```python
        action = self.ort_session.run([self.output_name], {self.input_name: obs_batch})[0]  # ② 交给 ONNX Runtime，拿回 14 个数
        self.last_action = action.copy()                          # ⑤ 记成“上一步动作”，下一圈要拼进观测里（第 15 章 15.3 节）
...

...
                for _ in range(decimation):                       # ④ 一个环境步里物理走 4 小步（decimation = 4，第 14 章 14.1 节）
```

## 本章小结

- **检查点**（`model_N.pt`）装着接着练所需要的一切（第 14 章 14.9 节）；**ONNX** 只装 actor 的那一串计算步骤和它要用的常数。
  一个是整间厨房（项目目录），一个是一张菜谱卡（build 出来的那个文件）；大小差大约 6 倍：critic 和 actor 差不多大是 2 份，Adam 的两本账再乘 3，2 × 3 = 6。
- ONNX 里的"一步"叫一个**算子**。迷你版两层，5 个算子：`Sub → Div → Gemm → Elu → Gemm`（2 个归一化 + 2 个 `Gemm` + 1 个 `Elu`）；
  真的那个四层，9 个算子：2 个归一化 + 4 个 `Gemm` + 3 个 `Elu`（最后一层不过门），两头是 `obs [1, 61]` 和 `actions [1, 14]`。
  `Gemm` 就是第 2 章 2.6 节的价格表 + 运费，`Elu` 就是第 6 章 6.1 节那道门。照着这个文件算的程序叫**推理运行时**（像浏览器之于 `.js`），它不需要 PyTorch。
- 归一化被**烘**在文件里（第 8 章 8.6 节）：61 个 μ 和 61 个"σ + 0.01"就在常数表里，加法在导出时就做完了。
  漏掉这两步，迷你版的第一个动作从 4.1353 rad 变成 40 rad——差 35.8647 rad = 36 − 0.1353：正数那家店把放大了的读数原样传了下去；而且仿真回放看不出来。
- **部署不采样**：导出时就把 14 个动作 σ 丢掉了，同一帧喂两次输出逐位相同。探索是训练的事（第 4 章 4.7 节、第 9 章 9.4 节）。
- 手写九步 = onnxruntime，差异在 $10^{-6}$（百万分之一）上下，那是**浮点误差**：float32 只存得下 7 位左右，一帧近 20 万次乘法各舍入一次、加的顺序又不同。
  核对用"最大误差 + 容差"，不要求逐位相同。
- 真机每 0.02 秒（20 毫秒，50 Hz）一圈：拼 61 个数 → ONNX → HOME + 动作 = 目标角 → 舵机追 0.02 秒（排练脚本里是物理走 4 小步）→ 记下这一步动作。
  几个策略共用这个 61 进 14 出的接口，所以能热切换（第 15 章 15.6、15.7 节）；但**同一格命令在不同策略里意思可以完全不同**——
  "全零"对坐下起立那个策略的意思是"站着"。
- 三种差异量级差得很远：浮点误差 $10^{-6}$，格子填错零点几到几 rad，漏归一化一大片都不对。中间那种，重新训练治不好。
  后两种在真模型上可能挨得很近，分辨时还要看喂进网络的 61 个数：是整体换了一套刻度（归一化），还是只有几项不对（格子）。
- 文件里还附着一小段**元数据**：8 块观测的名字和顺序、14 个关节名、14 个 HOME、`action_scale`。接口对不对，靠它逐块核对。
- 说"能用"之前，先说清这个 ONNX 是哪个检查点导出来的（拿第一层权重逐位比一比），再分清四种证据：
  跑得起来、数值一致、接口含义一致、行为达标——上一种不能替代下一种。

## 全书结束

翻回 README 开头那段话——"每隔 0.02 秒，每只机器人把 61 个数喂给一个神经网络；网络吐出 14 个数……
按一张评分表打一个分数……用 PPO 把网络的参数往以后得分更高的方向微调一点点"。
那段话的最后一句是"最后把网络导出成一个 `.onnx` 文件，装到真机上"——就是这一章刚刚做完的事。整段话到这里没有一个词还是黑箱。

四部书，四段路：

- **第 1 部 · 数学地基**（第 1–4 章）备齐了四样工具：量坡度的尺子、清单与价格表、一张写着"每个旋钮该往哪边拧"的梯度清单，
  和一口用来说"说不准下一次、说得清很多次"的钟。这一章里 `(12 − 10) ÷ 2`、`1×1 + 0×2 + 2×0.5 + 0.5`、$e^{-2} - 1$ 这几个手算，用的全是它们。
- **第 2 部 · 机器学习**（第 5–8 章）把工具接成一个圈：模型、损失、反向传播、优化器，外加给每一列各配一把尺子的归一化。
  ONNX 文件里那九个算子，正好就是第 8 章的两步加第 6 章的四层——一步不多，一步不少。
- **第 3 部 · 强化学习**（第 9–14 章）换掉了"标准答案"：没有老师，只有分数；于是有了价值、优势、比率和裁剪，
  最后汇成第 14 章那一圈训练回路。它转够几千圈，就留下一个检查点。
- **第 4 部 · 映射到 Microduck**（第 15–19 章）把这一切钉在一台真机器人上：61 项观测、一张评分表、
  一只会打滑会发热的舵机、一张按圈数换档的课程表，和这一章的那个 `.onnx`。

同一段话里的每一个词，现在都能展开成公式、代码和你自己算得出来的数字：

- **61 个数**：第 2、8、15 章。
- **吐出 14 个数**：第 4、6、17、19 章。
- **一个分数**：第 1、16 章。
- **往得分更高的方向**：第 3、7、10、11、12、13 章。
- **微调一点点**：第 5、14、18 章。

书到这里结束，那一圈却还在转：真机上每 0.02 秒，它就把这本书里的东西完整走一遍。
